# LoanCentral — Repository Audit & Repair Plan

Date: 2026-09-21
Branch audited: `upgrade/tested-bot-core` @ `560bed6` (working tree clean)
Scope: full repository inspection before the "dashboard-first" refactor.

---

## 0. Headline

**The codebase is in better shape than "negligent vibe coding" suggests.** The
suite is green (620/620), the working tree is clean, the security rules in
`docs/SECURITY.md` are genuinely enforced in most places, and the request-code
funding flow you wanted *already exists*.

The real problems are not sloppy features — they are **four structural gaps**:

1. **The tests mostly don't touch a database.** ~85% of the 620 tests replace the
   DB connection with `MagicMock()`. They assert that `commit()` was called, not
   that the SQL is valid or correct. This is why breakage can land while the
   suite stays green. Proven below with a live bug.
2. **There is no loan/request state machine.** Status rules are re-implemented ad
   hoc inside each function. `update_request_status` will move any request to any
   status, including `funded → open`.
3. **Business logic leaks into the route layer.** The request event timeline is
   written *only* by `api/app.py`. The bot and the service layer never write it.
4. **Reddit sync is a queue with no producer and no consumer.** The table and
   action types exist; nothing enqueues funding events and nothing ever sends them.

There is also **one product-rule conflict** in your brief that needs your decision
before I build it (section 2).

## 2. ⚠️ Product-rule conflict — needs your decision

Your brief, item 3:

> "Verified lenders can view available requests from their lender dashboard."

`VISION.md` explicitly forbids this:

> "A **lending marketplace** — do not show open borrower requests to lenders as a
> browsable list that lenders pick from. That is matchmaking and requires a
> financial license in most jurisdictions."

This is not an accident in the code — it is **actively enforced today**:

- `services.get_open_requests()` is exposed only at `GET /api/requests`, which is
  `@require_mod_api` (mods/admins only).
- The lender dashboard has no open-requests view at all.
- `cancel_loan_request` carries the comment: *"This is not a browsable marketplace
  action; it only records a decision on a known request."*

Someone deliberately built the funding flow as **request-code lookup** (lender
enters `REQ-0042` they already agreed to on Reddit) precisely to avoid being a
matchmaker. `docs/REQUEST_CODE_FLOW.md` confirms this was an owner decision on
2026-09-08.

**I have not built the browsable list.** Three options:

| Option | What it means |
|---|---|
| **A. Keep the boundary** (recommended) | Lender dashboard shows only *their* funded loans + a request-code lookup box. Everything else in your brief proceeds unchanged. |
| **B. Scoped list** | Lenders see only requests where the borrower has already engaged them (replied in-thread / lender was named). Closer to your ask, arguably still not matchmaking. |
| **C. Full browsable list** | Delivers your brief literally. This is the thing VISION.md says requires a license. Needs your explicit sign-off and probably legal advice. |

Everything else in your brief is compatible with the current product rules.

## 3. Confirmed bugs

### 3.1 `update_request_status` is broken on SQLite — always

`services.py:5193` builds notes with the Postgres-only escape-string literal
`E'\n'`. `local_db._translate_sql` does not translate it. Verified empirically:

```
SQLITE ERROR -> OperationalError near "'
'": syntax error
```

This is a **syntax** error, so it fires on every call regardless of data. Every
mod status change on the dev/demo dashboard fails with a 400. Production
(Postgres) is unaffected.

**Its tests pass** because they mock the cursor. This is the proof that the test
strategy is the core problem. Same bug at `api/app.py:1788` (`report_payment`).

### 3.2 Any logged-in user can dispute anyone else's loan

`api/app.py:1673` — `POST /api/loans/<id>/dispute`:

```python
borrower = data.get("borrower", session.get("username", "")).strip().lower()
```

The body value overrides the session. `services.dispute_loan` only checks that
the *supplied* name matches the loan's borrower — it never checks the caller.

So a logged-in user can flag any loan `disputed`, notify its lender, and —
worse — **the audit log records the victim as the actor**:

```python
log_audit(borrower, "borrower", "dispute_opened", ...)
```

That is audit falsification, not just status vandalism. Every other lender write
route correctly uses `_lender_write_actor()`; this one was missed.

### 3.3 No state machine → `funded → open → funded` double-funding

`update_request_status` validates only that the target status is in `_LR_STATUSES`.
There are no transition rules. A mod can move a funded request back to `open`,
after which `create_loan(request_id=...)` will happily create a **second** loan
from it and overwrite `funded_loan_id`, orphaning the first loan.

This is exactly the "paid loan accidentally changed back to funded" and "same
request funded twice" risk in your brief. It is mod-only, so it is a consistency
hole rather than an open vulnerability.

### 3.4 `loan_requests.reddit_post_id` has no unique constraint

`_ensure_loan_requests_table` creates a **non-unique** partial index.
`save_loan_request` dedupes with SELECT-then-INSERT, which is racy. Two near-
simultaneous imports of the same Reddit post create two request rows.

### 3.5 The bot never stores its own comment ID

`main.py:handle_new_post` calls `post.reply(...)` and discards the result. The
`loan_requests.reddit_comment_id` column exists but the bot path never fills it.
**Your goal 7 ("add or update a bot comment such as 'Funded by u/X'") cannot be
implemented for existing rows** — there is no stored comment to edit. New rows
need this captured from day one.

### 3.6 Nine analytics functions use `INTERVAL '...'`, unsupported by SQLite

`create_borrower_otp`, `create_magic_link`, `flag_possible_duplicates`,
`generate_request_quality_report`, `get_expanded_metrics`, `get_loan_request_queue`,
`get_request_analytics`, `queue_due_reminders`, `run_integrity_checks`.

All fine in production; all fail on the dev/demo SQLite dashboard. Again, hidden
by mocked tests.

## 4. Duplicate business logic

### 4.1 Two request code paths over one table

Both write to `loan_requests`, with different shapes, different validation, and
different event logging:

| | Bot path | Dashboard path |
|---|---|---|
| Create | `save_loan_request` (parses `[REQ]` title) | `create_loan_request` (explicit fields) |
| Read | `get_request_summary` (legacy key names) | `get_loan_request` (raw columns) |
| Events | `log_event` only | `log_event` only |
| Timeline | ❌ never | ❌ only from the route |

`CLAUDE.md` warns "`/api/requests/*` = OLD, `/api/loan-requests/*` = NEW. Never
mix them" — a warning sign taped over a structural problem rather than a fix.

### 4.2 The request timeline is written by the route layer, not the service layer

`log_request_event` is called from **`api/app.py` only** (lines 3499, 3583, 3626).
Consequence:

- Bot-created requests → **no timeline entry**
- Requests funded via `$fund` **or** via `/api/requests/<id>/fund` → **no "funded"
  timeline entry** (both go through `fund_loan_request` → `create_loan`)
- Only manual dashboard creation and mod status/link actions produce a timeline

So the request timeline you want to show lenders is currently missing its single
most important event. (The `audit_events` trail *is* written correctly by
`create_loan`, so money actions are not untraced — SECURITY rule 6 holds.)

### 4.3 Copy-pasted lender permission checks

`_lender_write_actor()` exists and is used by `/paid`, `/unpaid`, `/refunded`.
But `create_loan_manual` and `fund_request` re-implement the same four checks
inline. Two of the most sensitive routes are the two that bypass the shared
helper.

## 6. Security assessment

**Genuinely good** — do not rewrite these:

- Master API key is header-only, constant-time compared, and auto-disabled when
  unset or left at `changeme` (`api/app.py:44`).
- `perm_version` bounds session permission staleness to one request.
- `_is_lender_verified_fresh()` re-queries the DB on sensitive POSTs.
- All SQL is parameterized. I found no f-string SQL on user input.
- CSP, HSTS, `X-Frame-Options: DENY`, nosniff all set.
- Per-record ownership enforced in the service layer, not just the route layer.
- `_can_view_user_profile` requires a shared loan before one user sees another.

**Issues:**

| Sev | Issue |
|---|---|
| **High** | Dispute impersonation + audit falsification (§3.2) |
| **Medium** | CSRF defence is Origin/`Sec-Fetch-Site` only. If a request carries *no* `Origin`, *no* `Referer` and *no* `Sec-Fetch-Site`, it is allowed. Modern browsers always send `Sec-Fetch-Site` cross-site, so this is defensible — but there is no CSRF token. |
| **Medium** | `require_auth` means "logged in as anyone". ~40 routes rely on an inline check afterwards. One miss = one vulnerability (see §3.2). Needs an explicit decorator per role. |
| **Low** | `PUBLIC_DASHBOARD_TOKEN` grants dashboard access via `?access=<token>` in the **query string** — tokens land in logs and `Referer`. Dev-only, but SECURITY rule 8 says no keys in URLs. |
| **Low** | `.env` (production Postgres credentials) sits in the working directory. Correctly gitignored; flagging for awareness. |

## 7. Database consistency risks

1. **Four competing schema mechanisms**: `schema.sql` (15 tables) +
   `scripts/migrations/*.sql` (001–011) + 4 `_ensure_*_table()` helpers in
   `services.py` + ~25 `_ensure_column()` calls in `local_db.py`.
2. **No migration tracking table.** `run_migrations.py` re-runs all 11 files
   every time. Idempotent today only by convention — nothing enforces it.
3. **`schema.sql` is documented as stale** for `loan_requests` (DATA_MODEL.md
   says trust `services.py` instead). The schema file is not the schema.
4. **`users` is an aggregate cache** updated by hand-written `+`/`-` arithmetic
   in each service function. Any missed path silently drifts. `integrity.py`
   detects drift but nothing repairs it automatically.
5. **Invariants live in Python, not the database.** No CHECK constraint on
   `loans.status`, no partial unique index preventing two funded loans per
   request, no `UNIQUE` on `reddit_post_id`.

## 8. Where Reddit and the DB can disagree

The queue design is right; it is just unfinished.

- `reddit_actions` declares six action types. Only **three** are ever enqueued:
  `ban_user` (`api/app.py:1927`), `reminder_comment` (`scripts/reminder_job.py:85`),
  `flair_sync` (`services.py:1931`, on lender verification approval only).
- `flair_sync` on funding, `funded_comment`, `repaid_comment` are **declared but
  never produced**.
- **Nothing consumes the queue.** `update_reddit_action_status` is called only
  from a mod route where a human marks a row sent/skipped by hand.
- No retry count, no `next_attempt_at`, no error column on `reddit_actions`.
- No stored bot comment ID (§3.5).

So today: fund a loan on the dashboard → the Reddit post stays untouched and
still looks open. That is your goal 7, and it is genuinely unbuilt.

## 10. Proposed repair order

Dependency-ordered. Each phase ends green; nothing below starts until the phase
above is done.

### Phase 0 — Make the tests able to catch bugs *(prerequisite for everything)*
Without this, every later phase is unverifiable. Build a real-SQLite test
fixture (`test_request_funding_flow.py` already does this — promote its pattern),
port the highest-risk mocked tests onto it, and add the missing `conftest.py`.
**Then fix §3.1 and §3.6 and watch the new tests catch them.**

### Phase 1 — Schema stabilisation
Add a `schema_migrations` tracking table. Fold the four schema mechanisms into
one migration chain. Regenerate `schema.sql` from reality. Add constraints:
`UNIQUE(reddit_post_id)`, a partial unique index for one funded loan per request,
CHECK constraints on status columns. Non-destructive, additive only.

### Phase 2 — Loan & request state machines
One module defining allowed statuses and legal transitions for both loans and
requests. Every mutation routes through it. Kills §3.3 and the double-funding class.

### Phase 3 — Unify the request paths
Collapse `save_loan_request`/`create_loan_request` and
`get_request_summary`/`get_loan_request` into one service each. Move
`log_request_event` out of `api/app.py` into the service layer so the bot,
`$fund`, and the dashboard all produce identical timelines.

### Phase 4 — Security fixes
Fix §3.2. Replace the ~40 inline permission checks with explicit decorators
(`@lender_write_required`, etc.). Make `_lender_write_actor` mandatory, including
in `create_loan_manual` and `fund_request`.

### Phase 5 — Reddit sync worker
Producers on fund/repaid/default. A real queue consumer with retry count,
`next_attempt_at`, and an error column. Capture and store the bot's comment ID at
post time (§3.5). Handle deleted/removed posts. Failures stay in the queue and
never touch loan state.

### Phase 6 — Lender dashboard
Whatever you decide in §2, plus outstanding loans, history, timeline, and the
per-loan actions — all on the Phase 2/3 services.

### Phase 7 — Admin dashboard + ban system
Note this is **net-new**, not a repair (§5): `banned_users` table, a ban check in
the auth decorators, and admin UI for verify/revoke/ban/unban.

### Phase 8 — Cleanup
Remove the dead code from §9. Split `services.py` and `api/app.py` by domain —
**last**, once the state machine and service boundaries make the seams obvious.
